# ADR-0001: Domain model and AWS MVP architecture

## Status

Accepted

## Context

We are building an MVP mock-exam generator for IT certifications. The scope is intentionally narrow:

- Generate practice exams asynchronously for a catalog of certifications.
- List generated exams and expose PDF downloads via presigned API endpoints.
- AWS will host the serverless backend as part of a hands-on study session.

Authentication, pricing, analytics, and detailed failure handling are out of scope.

## Decisions

### 1. Certification vs. Exam

We split the catalog entry from the generated artifact.

- **Certification** describes the exam type: provider, code, name, and generation configuration.
- **Exam** is the generated, immutable practice test.

This keeps the API clear (`POST /v1/certifications` to create a type, `POST /v1/exams` to generate an instance) and lets the generator remain decoupled from the catalog.

### 2. The Exam is the generation job

Rather than maintaining a separate `Job` or `Task` resource, the `Exam` itself carries the generation status (`GENERATING`, `READY`, `FAILED`). A dedicated status endpoint returns only the status fields, and the full detail endpoint returns `409 Conflict` while the exam is not ready.

### 3. Asynchronous generation via SQS

The API accepts a generation request, writes the `Exam` metadata row, and sends a minimal message to an SQS standard queue:

```json
{ "examId": "...", "certificationId": "...", "correlationId": "..." }
```

A generator Lambda consumes the queue, loads the certification config, calls Amazon Bedrock once per question, builds the canonical JSON, renders the PDF, uploads both artifacts to S3, and marks the exam `READY`.

SQS is sufficient because there is a single consumer. EventBridge is overkill for the MVP.

### 4. DynamoDB for metadata, S3 for payloads

DynamoDB stores the `Exam` metadata row. S3 stores the canonical JSON and the generated PDF.

DynamoDB items are limited to 400 KB, which an exam with dozens of questions, explanations, and references can easily exceed. S3 is a better fit for the large, read-by-key payload.

### 5. Canonical exam format

The MVP supports only single-answer multiple-choice questions. The correct answer is stored inline in the question so future consumers (PDF renderer, simulator, etc.) can read a single artifact.

The canonical JSON carries a `schemaVersion` field (`1.0.0`) to support future format evolution.

### 6. Prompt template belongs to the Certification

The `Certification.config.promptTemplate` field drives the LLM prompts. Keeping it inside the certification means generation behavior is centralized and versioned with the exam type.

### 7. PDF is generated by the same generator

The generator produces both the canonical JSON and the PDF before marking the exam `READY`. The PDF contains the question set, a blank separator page, and an answer key with explanations at the end.

This avoids a multi-stage state machine and keeps the "exam is ready" notification unambiguous.

### 8. Public resources with basic protection

There is no user authentication. All exams and certifications are public. Abuse is mitigated by API Gateway throttling, WAF rate limiting, and a hardcoded `x-api-key` UUID passed from API Gateway to the Lambda layer.

### 9. API-only origin with CORS for cross-origin clients

The API lives on its own origin, e.g. `api.example.com`. CORS is configured at API Gateway so future web or mobile clients hosted elsewhere can consume it. This keeps the serverless backend decoupled from any client deployment and supports separate release cadences.

### 10. Path-based API versioning

The API is versioned from day one under `/v1/...`. This supports future breaking changes without reworking clients.

### 11. Auto-generated exam titles

Exam titles are derived from the certification name and an ISO-8601 timestamp. The client cannot override the title in the MVP.

### 12. Cursor-based listing with Lambda-side filtering

`GET /v1/exams` returns only ready exams by default, supports `status`, `provider`, and `certificationId` filters, and uses cursor-based pagination. A single DynamoDB GSI on `(status, createdAt)` is sufficient for the MVP; filtering by `provider` and `certificationId` is done in the Lambda.

### 13. Certification listing hides the prompt template

`GET /v1/certifications` returns active certifications, but omits the `promptTemplate` from the public response. The template is considered internal prompt engineering.

### 14. Exams are immutable but deletable

An exam cannot be edited after generation, but `DELETE /v1/exams/{id}` removes both the DynamoDB row and the S3 objects.

## Consequences

- The domain model is small and focused: `Certification`, `Exam`, `Question`, `AnswerOption`.
- The generator is cleanly decoupled from the API via SQS.
- The persistence split (DynamoDB + S3) handles the large exam payloads without hitting DynamoDB item-size limits.
- Failure handling is intentionally thin in the MVP; only `GENERATING` and `READY` are implemented. `FAILED` is reserved.
- The public, API-key-only model means the system relies on infrastructure-level controls for abuse prevention.
